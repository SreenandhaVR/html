Accessibility

Accessibility means making content usable by as many people as possible. While it mostly focuses on supporting people with disabilities, this practice benefits everyone. Even if you don't have a disability, you might be browsing on a mobile device with a smaller screen or using a slow internet connection. Accessible techniques can improve the experience for everyone in these situations as well. The core principle is simple: everyone should be able to access the web, and in some places it's actually the law. The W3C has a complete guide to accessibility laws and policies by country (opens in a new tab). The legal requirements vary by region, but they usually apply to government agencies and sectors such as banking, telecommunications, libraries, educational institutions, and transportation.

WCAG: The Web Content Accessibility Guidelines

The W3C created the Web Content Accessibility Guidelines (WCAG), which outline best practices for making web content accessible. The guidelines are extensive, so a good starting point is the "WCAG At a Glance" summary. WCAG is organized around four core principles, often remembered by the acronym POUR:

  • Perceivable — information and interface components must be presentable to users in ways they can perceive (e.g., text alternatives for images, captions for video).
  • Operable — interface components and navigation must be usable (e.g., everything works with a keyboard, no content that flashes in a way that could cause seizures).
  • Understandable — information and the operation of the interface must be understandable (e.g., predictable behavior, clear labels and instructions).
  • Robust — content must be robust enough to be interpreted reliably by a wide range of tools, including assistive technologies (e.g., valid, semantic HTML).

Accessible Rich Internet Applications (ARIA) Basics

Why ARIA exists

Informational websites tend to have a straightforward structure because their content is mostly static — it doesn't change very often. As a result, informational sites are often naturally more accessible than dynamic ones. Dynamic websites and web applications tend to be more complex because their content changes frequently. For example, on social media platforms, content is constantly updated in response to user actions like posting or liking something.

As the web became more advanced and interactive, new accessibility challenges appeared. Adding complex, dynamic features with JavaScript libraries sometimes resulted in less semantic HTML — markup that no longer clearly describes what each part of the page is or does. This makes it harder for screen readers and other assistive technologies to understand the page. ARIA (Accessible Rich Internet Applications) is a technology built to help solve this problem.

What ARIA actually is

ARIA is a set of special HTML attributes that add extra semantic meaning, without changing how an element looks or behaves visually. ARIA attributes fall into three categories: roles, properties, and states. Each is covered in detail below.

Important: ARIA changes only how an element is announced or exposed to assistive technology (like a screen reader). It does not add keyboard behavior, focus management, or styling on its own — you still have to implement that with HTML and JavaScript/CSS.

The Five Rules of ARIA Use

Rule 1: Use native HTML whenever you can

If a native HTML element or attribute already has the semantics and behavior you need, use it instead of repurposing another element and adding an ARIA role, state, or property to fake that behavior. 

<!-- Avoid this -->
<div role="button" tabindex="0" onclick="submitForm()">Submit</div>

<!-- Prefer this: a real button already has the role,
     keyboard support, and focus behavior built in -->
<button onclick="submitForm()">Submit</button>

Rule 2: Don't change native semantics unless you really have to

Avoid overriding the built-in role of an element unless there is a strong reason. For example, don't put role="heading" on a <div> when you could just use an <h2>, and don't add a conflicting role to an element that already has clear native semantics (like putting role="list" on a <button>).

Rule 3: All interactive ARIA controls must be usable with the keyboard

If you build a custom interactive widget using ARIA roles (for example, a custom dropdown with role="listbox"), you are responsible for making it fully operable with the keyboard — tabbing, arrow keys, Enter/Space, and Escape, wherever a sighted mouse user would expect them to work.

Rule 4: Don't use role="presentation" or aria-hidden="true" on a visible, focusable element

Doing so hides the element from assistive technology while leaving it visible and focusable to sighted keyboard users, which creates a confusing "invisible but focusable" element for screen reader users who tab onto it and hear nothing.

Rule 5: All interactive elements must have an accessible name

Buttons, links, form fields, and custom controls all need a text label that a screen reader can announce. This can come from visible text, an aria-label, or an aria-labelledby reference. 

<!-- Icon-only button needs an accessible name -->
<button aria-label="Close dialog">
  <svg aria-hidden="true">...</svg>
</button>

Common ARIA landmark roles

Landmark roles help screen reader users jump directly to major sections of a page, similar to how a sighted user visually scans a layout. Many of these now map to native HTML5 elements, so using the element is usually preferred over adding the role explicitly.

ARIA roles

A role tells assistive technology what an element is — its type or purpose — so a screen reader can announce it correctly and users know what kind of interaction to expect. Roles are set with the role attribute. Common roles include button, alert, navigation, dialog, tablist, and listbox.

Example: the button role

Sometimes you can't use a real <button> element — for example, a design system might require a <span> or <div> to be styled as a clickable control. In that case, role="button" tells assistive technology to treat it as a button. Remember: the role alone doesn't make it keyboard-operable — you still need tabindex="0" so it can receive keyboard focus, and a keydown handler so Enter and Space activate it, just like a native button would. 

<!-- A div styled to look like a button, made accessible with role="button" -->
<div
  role="button"
  tabindex="0"
  onclick="likePost()"
  onkeydown="if(event.key==='Enter'||event.key===' ') likePost()">
  Like
</div>

<!-- Still better: just use a real button whenever you can (Rule 1) -->
<button onclick="likePost()">Like</button>

Other common roles

  • role="alert" — marks urgent, time-sensitive content (like an error message) that should be announced immediately.
  • role="dialog" — marks a modal or popup window.
  • role="tab" / role="tablist" / role="tabpanel" — used together to build a custom tabbed interface.
  • role="navigation" — marks a block of navigation links (native equivalent: <nav>).
  • role="listbox" / role="option" — used for a custom dropdown or select-like widget.

ARIA properties

A property describes a characteristic of an element — something that's generally fixed for as long as the element exists, rather than something that toggles back and forth during use (that's what states are for, covered next). Common properties include aria-label, aria-labelledby, aria-describedby, and aria-required.

The aria-required property

aria-required="true" tells assistive technology that a form field must be filled in before the form can be submitted. This is important because a required field is often shown visually with just a red asterisk (*) — something a screen reader user can't see. Note that if you're using the native HTML required attribute, it already communicates this to assistive technology, so aria-required is mainly useful for custom form widgets that don't use native <input>/<select> elements. 

<label for="email">Email address *</label>
<input
  type="email"
  id="email"
  name="email"
  aria-required="true"
  required>

Other common properties

  • aria-label="..." — provides an accessible name when there's no visible text (e.g., an icon-only button).
  • aria-labelledby="id" — points to another element whose text should be used as the accessible name.
  • aria-describedby="id" — points to an element with extra descriptive text, like a hint or an error message.
  • aria-placeholder="..." — a hint shown when a custom (non-native) field is empty.

ARIA states

A state describes the current condition of an element — something that can change dynamically as the user interacts with the page, and that assistive technology needs to be told about each time it changes. Common states include aria-checked, aria-expanded, aria-hidden, aria-selected, and aria-disabled.

The aria-checked attribute

aria-checked indicates whether a checkbox-like or radio-like control is currently checked. It takes three possible values: "true" (checked), "false" (not checked), or "mixed" (a partially-checked state, used for a checkbox that represents a mix of checked and unchecked children — like a "select all" checkbox when only some items are selected). This attribute is mainly needed on custom checkbox or radio widgets built with roles like role="checkbox"; a native <input type="checkbox"> already communicates its checked state automatically and doesn't need it. 

<!-- A custom checkbox built without a native input -->
<div
  role="checkbox"
  aria-checked="false"
  tabindex="0"
  onclick="toggleCheckbox(this)">
  Subscribe to newsletter
</div>

<script>
function toggleCheckbox(el) {
  const isChecked = el.getAttribute('aria-checked') === 'true';
  el.setAttribute('aria-checked', String(!isChecked));
}
</script>

Other common states

  • aria-expanded="true|false" — indicates whether a collapsible section (like an accordion or dropdown) is currently open.
  • aria-hidden="true" — hides purely decorative content (like a background icon) from assistive technology. Never put this on a visible, focusable element (see Rule 4).
  • aria-selected="true|false" — indicates whether an option (e.g., a tab or a listbox item) is currently selected.
  • aria-disabled="true|false" — indicates that an element is present but currently not operable, while still keeping it visible and announced (unlike removing it or hiding it).
  • aria-live="polite|assertive" — marks a region so that screen readers announce content changes automatically, useful for things like toast notifications or form validation messages.
<!-- A live region example: screen readers announce
     this text whenever it changes, without needing focus -->
<div aria-live="polite">
  Your changes have been saved.
</div>

Additional Considerations

Why is a native <button> almost always better than a <div role="button">? A native button already comes with the correct role, keyboard support (Tab to focus, Enter/Space to activate), and built-in focus styling, all provided automatically by the browser. A <div role="button"> only gets the announced role — you have to manually add tabindex, keydown handling, and focus styling yourself, and it's easy to miss one of these and end up with a control that looks clickable but isn't fully usable.

What's the difference between an ARIA state and an ARIA property? A property describes a characteristic of an element that generally stays fixed for as long as the element exists, like aria-required marking a field as mandatory or aria-label giving it a name. A state describes a condition that changes dynamically as the user interacts with the page, like aria-checked toggling as a checkbox is clicked or aria-expanded flipping as a dropdown opens and closes. Because states change, your JavaScript is responsible for updating them every time the underlying condition changes.

Why is it dangerous to add aria-hidden="true" to a focusable element? Doing so removes the element from the accessibility tree while leaving it visible and reachable by keyboard Tab navigation. A screen reader user who tabs onto it will land on a control that announces nothing at all, which is confusing and can make part of the interface seem broken or unusable.

Which native HTML element replaces role="navigation"? The <nav> element already carries the navigation landmark role automatically, so it's preferred over adding role="navigation" to a generic <div>.

What does aria-live="polite" do, and when would you use it? It marks a region of the page so that whenever its content changes, a screen reader announces the new content automatically, without needing the user to have focus on that region. "Polite" means the announcement waits until the screen reader finishes whatever it's currently reading, rather than interrupting immediately. This is useful for things like a "changes saved" confirmation message or a form validation summary that appears after the user submits.

If you give a <div> role="button", what two things do you still need to add yourself to make it fully accessible? You need tabindex="0" so the element can receive keyboard focus, since a plain <div> isn't focusable by default. You also need a keydown handler that activates the button when the user presses Enter or Space, since the browser doesn't wire that up automatically the way it does for a real <button>.

Why doesn't a native <input type="checkbox"> need an aria-checked attribute? A native checkbox already exposes its checked state to assistive technology automatically through its built-in checked property, so adding aria-checked on top would be redundant. The attribute is really meant for custom widgets — elements built with role="checkbox" that don't use a real <input> under the hood and so have no native checked state to report.

What does aria-checked="mixed" represent, and when would you use it? It represents a partially-checked state, distinct from fully checked or fully unchecked. A common example is a "select all" checkbox at the top of a list: if some but not all of the items below it are checked, the "select all" checkbox is set to aria-checked="mixed" to communicate that in-between status rather than misleadingly showing it as fully checked or fully unchecked.

When is aria-required="true" actually necessary, versus when the native required attribute is enough? If you're using a real HTML form field, like <input required>, the native required attribute is already communicated to assistive technology on its own, so aria-required isn't needed. It becomes necessary on custom form widgets that aren't built from native <input>/<select> elements, since those have no built-in way to signal "this field is mandatory" to a screen reader without it.
